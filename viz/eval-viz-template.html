About these filters

Applies to every shortlist chart (pass rate through per-test breakdown). The tries-taken and failure-mode charts at the bottom use the full, unfiltered dataset and aren't affected. Exercise usefulness reflects the full model field regardless of the model filter — only the exercise and date filters change what it shows. The date range applies to when the eval ran, not the exercise's own content. Each task is labeled with its runner: ·A aider, ·H Harbor, ·HT Harbor with test calls (e.g. bowling (go) ·HT). The Runners checkboxes narrow the selected tests to one runner or both, without changing the selection, so the same tests can be viewed on aider, Harbor, or both. The default selection is the 20 exercises the most models have run, in every runner. Model scores pool every selected exercise, each graded against the other models on that same exercise.

Masks

Hide part of the selection from every view without changing it: unticking a runner hides its selected tests. Model groups overlap (a model can be Qwen3.8, Flash-Next and Coder at once), so each one cycles on click: ✓ include, ✗ exclude, blank neither. With any group included, only models in an included group are shown; an excluded group's models are always hidden (✓ Flash-Next + ✗ Coder = Flash-Next without Coder). Quant type and quant method are checkboxes: a model needs a ticked box in both (or, if in none of a section's groups, its "(other)" ticked). Ticking back restores the same selection.

What changing a setting did

The same gguf run at two settings combos, compared only on the tasks both ran (same runner/suite). A row is one change, e.g. effort low→xhigh: only pairs where exactly those settings differ and every other recorded setting is the same (a change that also moves the thinking budget is its own row); the setting filter shows every change that includes the chosen setting. Rows tagged + any other pool every comparison containing that one change, whatever else changed with it, for a setting's overall effect; the variants included are listed under the name, and expanded, each model's variants are pooled into one line (thin ticks show each variant). "N × M tasks" = N models with M shared tasks each on average (hover for each model's count). Columns are ordered by how many of the rows shown have a colored cell: those colored in over half the rows first, in a fixed order, then the rest by count; columns with none come last, grayed. Hover a column header for its full name, which direction is better, and its scale. Each stat is averaged per task first, so a task run three times doesn't outweigh one run once. Rates show the difference in points; everything else shows B vs A as a typical per-task ratio. Each stat is marked ↑ better / ↓ better (green = improvement, red = worse) or neutral (blue = up, teal = down). A row's cell pools its models by precision (a random-effects meta-analysis: a tight result counts for more than a noisy one, and models that genuinely disagree widen the interval): colored = significant at the chosen confidence level, stronger = bigger and clearer, gray number = not significant, muddy purple "+x / −y" = solid results in opposite directions (each side pooled on its own), empty = a change under 3 points / 5%. Rows are sorted by that evidence; by default a row needs a significant stat, and one with only 1–2 models also needs enough of it (that hides most one-model sampler sweeps; shown in gray with the checkbox). Click a row to see each model underneath (hover a name for details): each cell is that model's change with its interval (dot = estimate, colored if outside noise; scale shared down the column, zero in the middle). The runner rows compare the same gguf across harnesses on shared exercises, all settings pooled; the tag lists settings that also differ. Controls and open rows are remembered in this browser. Follows the filter panel (models, tests, runners, dates).

What stands out

Models: each gguf (its settings variants pooled) against every other model, on the tasks it ran: per task its mean vs the other models' (each model's own mean, averaged), pooled over tasks. Tests: each task against the same models' other tasks in its suite: per model its mean on this task vs its usual, pooled over models, so a test where models time out, glitch or spend more than usual stands out. Rows marked group do the same for several at once (ggufs sharing a name token, e.g. a family or quant; or a language / a whole suite), so two similar models stand out together instead of each diluting the other's baseline; expand a group for its members; on the tests tab, expand any row to see each model's own difference (one point per model, colored when past the column's big mark: 10 points / 25%). Cells and colors work as in the settings table (green better, red worse, neutral stats blue when up and teal when down; colored = significant at the chosen level; gray number = not). With this many rows, some colored cells are chance at any level, so the default here is 95% and rows are sorted by how much stands out. Intervals are normal approximations over tasks (models) / models (tests). Follows the filter panel (models, tests, runners, dates).

Capability score by model, on the selected 15-task view

Not a raw pass rate. The solid bar is Projected — the value shown and ranked by — a best-guess estimate for each untested task, built from that task's typical pass rate across every model, adjusted by how much this specific model has over- or under-performed on the tasks it HAS been tested on (that adjustment is itself distrusted until there's enough tested evidence to back it, so a model with only a couple of tested tasks projects close to the plain typical rate rather than confidently extrapolating a small sample). The thin gray bracket under the bar is the honest range it was chosen from: Proven (assumes every untested task fails) to Max (assumes every untested task passes) — both shown as their own columns on the right, along with how many tasks were actually Failed and Tested. All three collapse to one number once a model reaches full 15/15 coverage — at that point the bar is just the real, fully-known score, with no projection involved. Repeat runs of the same task are folded into one estimate per (model, task) pair, shrunk toward that task's own typical pass rate across every model — not toward a 50/50 coin flip, so a task tried only once isn't penalized just for lacking repeats. Tasks are weighted by how much they distinguish models and how consistent repeat runs on them are, so a hard, reliably model-splitting task counts for more than one everybody handles the same way. Ties are broken by average tries-to-pass. The main model's other 210 tasks aren't included here — see its full-run figure in the stat row above.

Pass within budget

Share of each model's attempts that had passed by a given amount of work. Hitting a limit (out of tries or test calls, out of time, out of tokens, cut off mid-reasoning) isn't counted as a failure: it says the attempt hadn't passed yet at that point, so it counts up to the work it had done and nothing after. An attempt that stopped on its own without passing, or broke, counts as a fail for good. So each curve's height at a budget is the estimated pass rate if every attempt had been given that much; where it levels off is the model's ceiling on these tasks, how fast it rises is its efficiency. Each task counts once per model however many attempts it has. Curves only compare fairly on the same tasks: the Common button in the filter panel picks those. Tries (aider) and test calls (Harbor) aren't the same unit, so the steps axis is best read one runner at a time.

Generation speed on passing runs

Completion tokens per second, averaged over each model's passing shortlist runs. The time is what the model spent on requests when the eval proxy measured it (newer Harbor runs, and newer aider runs once run.sh records it), else the run's wall-clock time, which also counts tool and test execution. Duration and token counts both include every internal retry within a run, so this cancels out most of the "more tries = more work" effect — it's throughput, not luck.

Tokens generated per passing run

Tokens per pass, normalized to each exercise's own difficulty — 1.0× is the average token cost among models that passed that exercise, so a model that mostly solved cheap exercises isn't flattered and one that solved expensive ones (like clock, ~2.4× the shortlist average) isn't unfairly penalized. All three panels share one column order, so you can see whether a model's token cost, wall-clock cost, and retry cost all tell the same story. Each faint dot is one passing run; the bold dot per model is the average, connected to trace the trend. Tries taken is jittered slightly to keep identical values from stacking into one dot.

Pass / fail by task × model

Rows ranked top-to-bottom by task quality (discriminative power, rewarded; cost, inconsistency and how often models recall the exercise from memory, penalized — same composite as the "quality" column below). Columns ranked left-to-right by the option below (default: average tokens generated, cheapest model first). Green = passed (majority of runs, for tasks re-run more than once), shaded by how many tries it took on average — dark green means it passed fast, pale green means it barely scraped by. Red = failed. A cell that's been re-run and landed some of each way — neither a clean pass nor a clean fail — gets a diagonal hatch so it doesn't read as identical to a clean result at a glance; the pass/total number underneath (shown whenever a task was attempted more than once) is the exact split. Color fails by can split fails into ones stopped by a limit (out of tries, test calls, time or tokens: the attempt hadn't passed yet) and ones that failed on their own (the agent declared done with failing tests, or its output broke), going by what most of the cell's failed runs did. A small dot in the corner marks a cell with at least one run that ended a given way or hit a given problem, picked in Mark cells with (default: hit the time limit; a run can carry a flag and still pass). A folded top-left corner marks a cell where at least half the runs have low trust: the model recalled or downloaded the answer (seen in Harbor, or inferred for aider from the same model's Harbor runs), so the result counts for little in capability scores. How attempts ended

For the selected models, tasks and dates: how each row's attempts ended (passed, stopped by a limit, or failed on its own), then how often each problem showed up along the way, as a share of the row's attempts (passes included). A cell is shaded by how many times the overall rate for that problem it is: dark = this row has a lot more of it than the selection as a whole. Thinking cut-offs are the exception: that column is the share of thinking blocks the reasoning budget cut off, since one cut-off anywhere marks a whole multi-turn trial. Read it both ways: shading concentrated in one model's row is that model's habit; shading in one task's row across many models points at the task or the harness (a limit set too tight, a broken verifier) rather than any model. Each attempt counts once (latest per seed). End reasons and flags are defined in outcomes.py.

Exercise usefulness — is this task worth keeping?

Each of the 15 currently selected tasks with surviving data, plotted by cost (average wall-clock time, all models) against how much it splits the model field (0 = every model landed the same way, pass or fail; 1 = an even 50/50 split — the most information a task can give). A task voided entirely (e.g. by a harness bug) is left off rather than shown as a false 0/0. Bubble size is attempt count; color is which way the split leans. Cheap + high-split (top-left) is the best-value task; expensive + low-split (bottom-right) is the prime candidate to cut. The table's Quality column folds discriminative power, cost, flakiness and recall rate into one number (higher = better) — it's what orders the heatmap's rows above. Score weight is a related but distinct number — discriminative power × reliability × (1 − ½ recall), cost excluded — it's how much this task counts toward the "Capability score by model" chart above. Flakiness is shrunk toward the typical (usually low) flakiness across every other exercise, weighted by how many models actually re-ran this one — a task re-run by exactly one model that split 1/2 isn't treated as confidently "maximally flaky" the way one re-run by seven models with a consistent mixed result is. Timeout rate is what fraction of this task's failures were the harness bailing on its max-duration limit rather than the model actually failing on its own (count in parentheses) — unlike Flakiness, this isn't folded into Quality or Score weight, since a model that reliably always times out on a task is consistent, not flaky; a high rate here is a hint the duration budget may be too tight for this specific task, worth checking before reading too much into its other numbers. Recall rate is how often a model recognised the exercise and recalled the upstream solution (it named Exercism or its specs, then wrote out remembered code or test cases). Only Harbor trajectories show this, but it's counted per exercise and applies to the aider variant too. It's shrunk toward the overall rate, and exercises with no Harbor attempts (marked *) get that overall rate. A task models reliably recall tests memory, not ability, so it lowers Quality, and scales Score weight by (1 − ½ × recall rate). The small ◆ diamond tied to each dot by a dashed line is a second, independent split: tries-discriminative — not whether models pass or fail, but how much their average tries-to-pass on this task actually spread out (0 = everyone needed about the same tries even if some failed, 1 = a wide spread from fast to slow). A task can split cleanly on pass/fail (high discriminative) while everyone who passes takes about the same tries (low tries-discriminative), or the reverse — everyone eventually passes, but how long it takes them varies a lot. It's omitted for a task fewer than 2 models have passed yet, since there's nothing to compare. The dot's height is the pass/fail split blended (75/25) with the other spread signals (tries, and how much models differ in duration and output tokens); the □ square shows that 25% part on its own (the mean of tries, duration and token spread; the diamond is just its tries component), so a dot pulled up or down from its pass/fail value can be traced to it.
